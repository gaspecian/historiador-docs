# GHCR Release Pipeline Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add a GitHub Actions workflow that publishes signed, multi-arch container images for `api`, `mcp`, and `web` to GHCR on stable tags and beta branches, with SBOM attestations, Trivy gating, and an autogenerated GitHub Release for stable tags.

**Architecture:** Single workflow file `.github/workflows/release.yml` with two jobs. The `publish` job runs a matrix over the three services and handles build → push → SBOM → cosign sign → cosign attest → Trivy scan. The `release-notes` job depends on `publish` and runs only on `refs/tags/v*` (stable channel only). Stable tag refs and beta branch refs are unified inside `docker/metadata-action@v5` via conditional `enable` flags so a single workflow handles both channels.

**Tech Stack:** GitHub Actions, Docker Buildx (multi-arch via QEMU), GHCR, cosign keyless OIDC, Anchore SBOM action, Trivy, softprops/action-gh-release.

**Spec:** [artifacts/specs/2026-04-25-ghcr-release-pipeline-design.md](../specs/2026-04-25-ghcr-release-pipeline-design.md)

# .trivyignore — CVE suppression list for the Trivy gate in release.yml.
#
# Trivy fails the release workflow on HIGH/CRITICAL CVEs. This file is the
# escape valve for cases where an upstream image carries a CVE that has no
# fix yet, where the affected code path is provably unreachable, or where
# the vulnerability is otherwise an accepted known limitation.
#
# Format: one CVE id per line. Optional inline comment after `#`.
# Example:
#   CVE-2024-12345  # affects libfoo; we don't link libfoo. 2026-04-25 — gabriel
#
# RULES:
# 1. Every entry MUST have a one-line justification (CVE id, reason, date,
#    reviewer). No silent suppressions.
# 2. Re-evaluate suppressions before each stable release; remove entries
#    where an upstream fix is now available.
```

## Task 2: Create `.github/workflows/release.yml`

Built incrementally — append a section, validate with `actionlint`, then
move on. Each step is bite-sized and the file is in a valid state after
every actionlint pass.

**Files:**
- Create: `.github/workflows/release.yml`

- [ ] **Step 1: Create the file with workflow header**

Write to `.github/workflows/release.yml`:

```yaml
name: Release

on:
  push:
    tags: ['v*.*.*']
    branches: ['release/beta-*']

concurrency:
  group: release-${{ github.ref }}
  cancel-in-progress: false

permissions:
  contents: write        # release-notes job creates a GitHub Release
  packages: write        # GHCR push
  id-token: write        # cosign keyless via GitHub OIDC
  attestations: write    # SBOM attestation

jobs:
  publish:
    name: Build and publish ${{ matrix.service }}
    runs-on: ubuntu-latest
    strategy:
      fail-fast: false
      matrix:
        include:
          - service: api
            dockerfile: Dockerfile.rust
            build-args: BIN_NAME=api
          - service: mcp
            dockerfile: Dockerfile.rust
            build-args: BIN_NAME=mcp
          - service: web
            dockerfile: apps/web/Dockerfile
            build-args: ""
    steps:
      - uses: actions/checkout@v4
```

`fail-fast: false` lets a Trivy block on one service still permit the others
to publish — debugging a single noisy CVE shouldn't void the whole release.

`cancel-in-progress: false` ensures concurrent tag and beta pushes don't
cancel each other; each release run goes to completion.

- [ ] **Step 2: Validate with actionlint**

```bash

Expected: no output (success). actionlint may warn that the publish job

- [ ] **Step 3: Append QEMU, Buildx, GHCR login, and beta-version steps**

The `Compute beta version` step runs only on beta-branch refs, so for stable

the next step uses that emptiness as the discriminator between channels.

- [ ] **Step 5: Append `metadata-action` with combined stable + beta tag rules**

Append to the same `steps:` list:

```yaml
      - name: Compute image metadata
        id: meta
        uses: docker/metadata-action@v5
        with:
          images: ghcr.io/${{ github.repository }}/${{ matrix.service }}
          tags: |
            type=semver,pattern={{version}}
            type=semver,pattern={{major}}.{{minor}}
            type=semver,pattern={{major}}
            type=raw,value=${{ steps.beta.outputs.version }}-beta,enable=${{ steps.beta.outputs.version != '' }}
            type=raw,value=${{ steps.beta.outputs.version }}-beta.${{ github.run_number }},enable=${{ steps.beta.outputs.version != '' }}
            type=raw,value=beta,enable=${{ steps.beta.outputs.version != '' }}
          flavor: |
            latest=auto
```

Tag emissions by trigger (matches the spec):

| Trigger                                       | Tags emitted (per service)                                |
| --------------------------------------------- | --------------------------------------------------------- |
| `v1.2.3`                                      | `1.2.3`, `1.2`, `1`, `latest`                             |
| `v1.2.3-rc1` (pre-release)                    | `1.2.3-rc1` only                                          |
| `release/beta-1.2.0` push, run #42            | `1.2.0-beta`, `1.2.0-beta.42`, `beta`                     |

`type=semver` rules silently no-op on branch refs; `type=raw` rules silently
no-op when their `enable` evaluates false. `latest=auto` is the
metadata-action default — made explicit here — and intentionally does NOT
move `latest`/`1`/`1.2` on pre-releases.

- [ ] **Step 9: Append SBOM, cosign install, sign, and attest steps**

Append:

```yaml
      - name: Generate SBOM
        uses: anchore/sbom-action@v0
        with:
          image: ghcr.io/${{ github.repository }}/${{ matrix.service }}@${{ steps.build.outputs.digest }}
          format: spdx-json
          output-file: sbom-${{ matrix.service }}.spdx.json

      - name: Install cosign
        uses: sigstore/cosign-installer@v3

      - name: Sign image
        env:
          DIGEST: ${{ steps.build.outputs.digest }}
        run: |
          cosign sign --yes \
            "ghcr.io/${{ github.repository }}/${{ matrix.service }}@${DIGEST}"

      - name: Attest SBOM
        env:
          DIGEST: ${{ steps.build.outputs.digest }}
        run: |
          cosign attest --yes \
            --predicate "sbom-${{ matrix.service }}.spdx.json" \
            --type spdx \
            "ghcr.io/${{ github.repository }}/${{ matrix.service }}@${DIGEST}"
```

`--yes` skips cosign's interactive confirmation prompt (required in CI).
Keyless signing via the GitHub OIDC token requires `id-token: write`, which
is declared at the workflow level in Step 1.

- [ ] **Step 11: Append Trivy scan step**

Append:

```yaml
      - name: Trivy vulnerability scan
        uses: aquasecurity/trivy-action@master
        with:
          image-ref: ghcr.io/${{ github.repository }}/${{ matrix.service }}@${{ steps.build.outputs.digest }}
          severity: HIGH,CRITICAL
          exit-code: '1'
          ignore-unfixed: false
          trivyignores: .trivyignore
```

The scan runs against the already-pushed manifest so it inspects the actual
arch-specific layers. If a HIGH/CRITICAL CVE is found that isn't in
`.trivyignore`, the job fails. The image is in the registry but unverified —
operator triages by adding a justified ignore entry or waiting for an
upstream fix and re-tagging.

- [ ] **Step 13: Append the `release-notes` job**

Append to the workflow file at the top-level `jobs:` map (after the closing
of the `publish` job's `steps:` list):

```yaml
  release-notes:
    name: Create GitHub Release
    needs: publish
    if: startsWith(github.ref, 'refs/tags/v')
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0  # full history; required for changelog generation

      - name: Compute version (strip leading v)
        id: ver
        run: echo "tag=${GITHUB_REF_NAME#v}" >> "$GITHUB_OUTPUT"

      - name: Create GitHub Release
        uses: softprops/action-gh-release@v2
        with:
          generate_release_notes: true
          prerelease: ${{ contains(github.ref_name, '-') }}
          body: |
            ## Container images

            ```
            docker pull ghcr.io/${{ github.repository }}/api:${{ steps.ver.outputs.tag }}
            docker pull ghcr.io/${{ github.repository }}/mcp:${{ steps.ver.outputs.tag }}
            docker pull ghcr.io/${{ github.repository }}/web:${{ steps.ver.outputs.tag }}
            ```

            All images are signed (cosign keyless) with SPDX SBOM attestations.
            Verify before deploying:

            ```
            cosign verify ghcr.io/${{ github.repository }}/api:${{ steps.ver.outputs.tag }} \
              --certificate-identity-regexp 'https://github.com/${{ github.repository }}/.github/workflows/' \
              --certificate-oidc-issuer 'https://token.actions.githubusercontent.com'
            ```
```

Notes:
- `needs: publish` waits for **all** matrix entries to succeed. If Trivy
  fails on one service, the Release is not created — preventing a Release
  page that claims all images shipped when only some did.
- `prerelease: ${{ contains(github.ref_name, '-') }}` marks RC tags
  (`v1.2.3-rc1`) as pre-releases on the GitHub UI, which prevents GitHub's
  "Latest release" pointer from being moved to a pre-release.
- The `Compute version` step strips the leading `v` because GHCR tags don't
  carry it (metadata-action drops it), so the `docker pull` commands in the
  Release body must use the stripped form.

```markdown
## Cutting a release

Two channels are wired into `.github/workflows/release.yml`: stable
(`v*.*.*` tags) and beta (`release/beta-*` branches). Both produce signed,
multi-arch container images for `api`, `mcp`, and `web` in GHCR, with SBOM
attestations and a Trivy vulnerability gate.

### Stable release

1. Make sure `main` (or the branch you intend to release) is in the state
   you want to ship.
2. Cut a signed, annotated tag and push it:

   ```bash
   git tag -s v1.2.3 -m "v1.2.3"
   git push origin v1.2.3
   ```

3. Watch the `Release` workflow in the Actions tab. On success, a GitHub
   Release page is created automatically at
   `https://github.com/<owner>/<repo>/releases/tag/v1.2.3` with an
   autogenerated changelog and `docker pull` / `cosign verify` instructions.

Pre-release tags like `v1.2.3-rc1` follow the same path but are marked as
pre-releases on the Releases page and do not move `latest`/`1.2`/`1`.

### Beta release

1. Branch from wherever you want to bake the beta:

   ```bash
   git switch -c release/beta-1.2.0
   git push -u origin release/beta-1.2.0
   ```

2. Each push to that branch produces these tags (per service):
   - `1.2.0-beta` — moves on each push
   - `1.2.0-beta.<run_number>` — immutable, lets consumers pin a build
   - `beta` — moves on each push (latest beta of any version)

3. When the beta is ready to promote, cut a stable `v1.2.0` tag from the
   beta branch (or after merging it into `main`) following the stable
   release steps.

### Verifying a release before deploying

```bash
cosign verify ghcr.io/<owner>/<repo>/api:1.2.3 \
  --certificate-identity-regexp 'https://github.com/<owner>/<repo>/.github/workflows/' \
  --certificate-oidc-issuer 'https://token.actions.githubusercontent.com'
```

Replace `<owner>/<repo>` with the actual repository slug.

### One-time setup after the first release

GHCR creates packages as **private** on first push regardless of repository
visibility. After the first successful `release.yml` run:

1. Visit `https://github.com/<owner>?tab=packages`.
2. For each of `api`, `mcp`, `web`: Settings → Change visibility → Public.
3. Optional: link each package to the source repo (improves discovery; adds
   a "Used by" panel).
```
