# GHCR Release Pipeline — Design

**Date:** 2026-04-25
**Branch:** `feature/ci-cd`
**Status:** Approved; plan to follow

## Goal

GitHub Actions publishes signed, multi-architecture (linux/amd64 +
linux/arm64) container images for the three deployable services to GitHub
Container Registry, with SPDX SBOM attestations, gated by a Trivy
vulnerability scan that fails the publish on HIGH/CRITICAL CVEs. Two release
channels:

- **Stable** — triggered by pushing a `v*.*.*` git tag. Produces semver-tagged
  images and a GitHub Release with autogenerated changelog.
- **Beta** — triggered by pushing to a `release/beta-<version>` branch.
  Produces beta-tagged images for pre-release validation. No GitHub Release
  is created for betas.

Out of scope: continuous deployment to a live environment. "CD" here ends at
"image is in the registry, signed, and verifiable, and (for stable) the
release is announced."

## Context

The existing `.github/workflows/ci.yml` already runs the project's quality
gates (Rust fmt/clippy/audit/test/release-build, Node install/lint/types
freshness check, Docker smoke-build of all three images with `push: false`).
That workflow continues to run on PR and on push to `main` and is **not**
modified by this work — release publication is a separate concern with a
separate trigger, and coupling them risks "fix CI to ship a release" footguns.

The product produces three container images:

| Service | Dockerfile             | Build arg            |
| ------- | ---------------------- | -------------------- |
| `api`   | `Dockerfile.rust`      | `BIN_NAME=api`       |
| `mcp`   | `Dockerfile.rust`      | `BIN_NAME=mcp`       |
| `web`   | `apps/web/Dockerfile`  | —                    |

These three are the entirety of the publish surface. The vector store
(Chronik-Stream, per ADR-007) is consumed as an upstream image
(`ghcr.io/lspecian/chronik-stream`) — we don't rebuild or republish it.
Postgres and Ollama are likewise upstream images. `docker-compose.prod.yml`
references the three published images via an `IMAGE_TAG` environment
variable, so the output of this pipeline plugs directly into existing
deployment docs without compose changes.

## Decisions

| # | Decision                              | Choice                              |
| - | ------------------------------------- | ----------------------------------- |
| 1 | Stable publish trigger                | Semver git tags (`v*.*.*`)          |
| 2 | Beta publish trigger                  | Push to `release/beta-<version>` branches |
| 3 | Architectures                         | `linux/amd64` + `linux/arm64`       |
| 4 | Visibility                            | Public                              |
| 5 | Supply-chain hardening                | Cosign keyless sign + SPDX SBOM + Trivy gate (HIGH/CRITICAL) — applied identically to stable and beta |
| 6 | Release announcement                  | GitHub Release with autogenerated changelog (`softprops/action-gh-release`) on stable tags only |

## Architecture

### New workflow: `.github/workflows/release.yml`

**Trigger**

```yaml
on:
  push:
    tags: ['v*.*.*']
    branches: ['release/beta-*']
```

No `workflow_dispatch` for now — keeps the trigger surface small and the
audit trail clean. Adding manual dispatch is trivially additive later.

**Permissions** (job-scoped, principle of least privilege)

```yaml
permissions:
  contents: write        # checkout + create GitHub Release on stable tags
  packages: write        # GHCR push
  id-token: write        # cosign keyless via GitHub OIDC
  attestations: write    # SBOM attestation
```

`contents: write` (rather than `read`) is required by the release-notes job
that creates the GitHub Release. The publish job itself only needs `read`,
but workflow-level permissions are simpler than per-job permission blocks
and the elevation is tightly scoped (`softprops/action-gh-release` only
writes to the Releases API).

**Job structure**

Two jobs:

1. **`publish`** — matrix over the three images. Builds, pushes, signs,
   attests SBOM, scans. Runs on both stable and beta triggers.
2. **`release-notes`** — single job that depends on `publish`. Runs only on
   stable tag pushes. Creates the GitHub Release with autogenerated
   changelog plus a body section listing the published images and
   `cosign verify` instructions.

```yaml
strategy:
  fail-fast: false
  matrix:
    include:
      - service: api
        dockerfile: Dockerfile.rust
        build-args: BIN_NAME=api
      - service: mcp
        dockerfile: Dockerfile.rust
        build-args: BIN_NAME=mcp
      - service: web
        dockerfile: apps/web/Dockerfile
        build-args: ""
```

`fail-fast: false` so that a Trivy block on one image still lets the others
publish — debugging a single noisy CVE shouldn't void the whole release.

**`publish` job steps (in order)**

1. `actions/checkout@v4`
2. `docker/setup-qemu-action@v3` — emulation for arm64
3. `docker/setup-buildx-action@v3` — multi-arch driver
4. `docker/login-action@v3` — log into `ghcr.io` using `GITHUB_TOKEN`
5. **Compute beta version** — when the ref is a beta branch, extract the
   version suffix into a step output for use by metadata-action:

   ```yaml
   - name: Compute beta version
     id: beta
     if: startsWith(github.ref, 'refs/heads/release/beta-')
     run: echo "version=${GITHUB_REF_NAME#release/beta-}" >> "$GITHUB_OUTPUT"
   ```

6. `docker/metadata-action@v5` — produce tag list (see Tag plan below)
7. `docker/build-push-action@v6` — build + push, multi-arch, GHA cache
8. `anchore/sbom-action@v0` — generate SPDX JSON for the pushed digest
9. `sigstore/cosign-installer@v3` — install cosign CLI
10. `cosign sign --yes` — sign the pushed digest, keyless OIDC
11. `cosign attest --predicate sbom.spdx.json --type spdx --yes` — attach SBOM
12. `aquasecurity/trivy-action@master` — scan pushed image, `severity: HIGH,CRITICAL`, `exit-code: 1`, honours `.trivyignore`

**`release-notes` job steps**

```yaml
release-notes:
  needs: publish
  if: startsWith(github.ref, 'refs/tags/v')
  runs-on: ubuntu-latest
  steps:
    - uses: actions/checkout@v4
      with:
        fetch-depth: 0  # full history; needed for changelog generation
    - uses: softprops/action-gh-release@v2
      with:
        generate_release_notes: true
        body: |
          ## Container images

          ```
          docker pull ghcr.io/${{ github.repository }}/api:${{ github.ref_name }}
          docker pull ghcr.io/${{ github.repository }}/mcp:${{ github.ref_name }}
          docker pull ghcr.io/${{ github.repository }}/web:${{ github.ref_name }}
          ```

          All images are signed (cosign keyless) with SPDX SBOM attestations.
          Verify before deploying:

          ```
          cosign verify ghcr.io/${{ github.repository }}/api:${{ github.ref_name }} \
            --certificate-identity-regexp 'https://github.com/${{ github.repository }}/.github/workflows/' \
            --certificate-oidc-issuer 'https://token.actions.githubusercontent.com'
          ```
```

`generate_release_notes: true` invokes GitHub's built-in changelog
generation (PR titles since the previous matching tag, grouped by label).
The custom `body:` is appended *after* the autogenerated section — it
doesn't replace it. Conventional-commits style commit subjects (already
in use in this repo) yield readable output without further configuration.

**Why not `release-please`?** It's the more powerful option (manages
`CHANGELOG.md`, opens release PRs, automates version bumps), but it
requires committing to its workflow throughout the repo and adds a second
recurring automation. For "publish images + readable release notes,"
`softprops/action-gh-release` is the right ladder rung. Adopting
`release-please` later is a separate, additive decision.

**Tag plan**

`docker/metadata-action@v5` configured with conditional rules covering both
channels in a single configuration:

```yaml
images: ghcr.io/${{ github.repository }}/${{ matrix.service }}
tags: |
  # Stable: tag refs matching v*.*.*
  type=semver,pattern={{version}}
  type=semver,pattern={{major}}.{{minor}}
  type=semver,pattern={{major}}
  # Beta: branch refs matching release/beta-<version>
  type=raw,value=${{ steps.beta.outputs.version }}-beta,enable=${{ steps.beta.outputs.version != '' }}
  type=raw,value=${{ steps.beta.outputs.version }}-beta.${{ github.run_number }},enable=${{ steps.beta.outputs.version != '' }}
  type=raw,value=beta,enable=${{ steps.beta.outputs.version != '' }}
flavor: |
  latest=auto
```

`type=semver` rules silently no-op on branch refs; `type=raw` rules
silently no-op when their `enable` evaluates false. One configuration
handles both paths.

**Tag outputs by trigger**

Stable tag `v1.2.3`:

- `ghcr.io/gaspecian/historiador-docs/api:1.2.3`
- `ghcr.io/gaspecian/historiador-docs/api:1.2`
- `ghcr.io/gaspecian/historiador-docs/api:1`
- `ghcr.io/gaspecian/historiador-docs/api:latest`

Stable pre-release tag `v1.2.3-rc1`:

- `ghcr.io/gaspecian/historiador-docs/api:1.2.3-rc1`

Beta branch push to `release/beta-1.2.0` (run number 42):

- `ghcr.io/gaspecian/historiador-docs/api:1.2.0-beta` (moves on each push)
- `ghcr.io/gaspecian/historiador-docs/api:1.2.0-beta.42` (immutable)
- `ghcr.io/gaspecian/historiador-docs/api:beta` (moves; latest beta of any version)

`latest=auto` (the metadata-action default, made explicit here)
intentionally **does not** move the `latest`, `1`, `1.2`, or `beta` tags
on stable pre-release tags — only stable semver advertises itself as the
current version. metadata-action also strips the leading `v` from the
source ref by convention.

### `.trivyignore`

Empty on first commit, with a comment header explaining the format and a
note that any addition requires a one-line justification (CVE id + reason +
date + reviewer). The file is the documented escape valve when an upstream
fix isn't available; making it empty by default forces a deliberate decision
rather than silent suppression.

### `CONTRIBUTING.md` addition

Append a short "Cutting a release" section covering both channels:

**Stable release**

1. Bump versions where appropriate (no automation here yet).
2. `git tag -s v1.2.3 -m "v1.2.3"` (signed annotated tag).
3. `git push origin v1.2.3`.
4. Watch the `release` workflow. The matching GitHub Release is created
   automatically when `publish` succeeds.

**Beta release**

1. From `develop` (or wherever betas branch from), `git switch -c release/beta-1.2.0`.
2. `git push -u origin release/beta-1.2.0`.
3. Each subsequent push to that branch produces a new immutable
   `1.2.0-beta.<run>` tag and moves the `1.2.0-beta` and `beta` tags.
4. When the beta is ready to promote, cut a stable `v1.2.0` tag from the
   beta branch (or after merging it back) following the stable steps above.

First-time releases require a manual visibility flip in GHCR (see runbook).

### One-time, post-first-release manual step

GHCR creates packages as **private** on first push, regardless of repo
visibility. After the first successful `release.yml` run:

1. Visit `https://github.com/gaspecian?tab=packages`.
2. For each of `api`, `mcp`, `web`: Settings → Change visibility → Public.
3. Optional: link each package to the source repo (improves discovery, adds
   "Used by" panel).

This is documented as a release runbook item, not automated.

## Components and Boundaries

| Unit                              | Purpose                                              | Inputs                          | Outputs                                |
| --------------------------------- | ---------------------------------------------------- | ------------------------------- | -------------------------------------- |
| `release.yml` workflow            | Orchestrate publish on tag or beta-branch push       | Tag ref or branch ref           | Pushed images + signatures + SBOMs (+ Release on stable) |
| `Compute beta version` step       | Parse branch suffix into version output              | `GITHUB_REF_NAME`               | `steps.beta.outputs.version`           |
| `metadata-action` step            | Compute tag list (handles both channels)             | Tag/branch ref + beta version   | Tag/label set for build-push           |
| `build-push-action` step          | Build multi-arch and push                            | Tag list, Dockerfile, build-args| Image manifest + per-arch digests      |
| `sbom-action` step                | Produce SPDX SBOM                                    | Image digest                    | `sbom.spdx.json` artifact              |
| `cosign sign` / `cosign attest`   | Sign image; attach SBOM as attestation               | Digest, SBOM, OIDC token        | Signature + attestation in registry    |
| `trivy-action` step               | Vulnerability gate                                   | Image digest, `.trivyignore`    | Pass / fail (exit code)                |
| `release-notes` job               | Create GitHub Release with autogenerated changelog (stable only) | Tag ref, full git history | GitHub Release page with notes + image pull/verify instructions |
| `.trivyignore`                    | Triaged-exception register                           | Manual entries                  | Suppressions read by Trivy             |

Each unit communicates through artifacts in the workflow run or registry
state — no shared in-memory mutable state between steps beyond `outputs`.

## Data Flow

**Stable channel:**

```
git tag v1.2.3 → push origin v1.2.3
        │
        ▼
release.yml > publish (matrix: api, mcp, web)
        │
        ├── metadata-action ─► tag list {1.2.3, 1.2, 1, latest}
        ├── build-push ─► ghcr.io/<owner>/<repo>/<service>:<each tag>
        │                    (linux/amd64 + linux/arm64 manifest list)
        ├── sbom-action ─► sbom.spdx.json (run artifact)
        ├── cosign sign ─► signature in registry (.sig tag)
        ├── cosign attest ─► SBOM attestation in registry (.att tag)
        └── trivy ─► pass / fail-on-HIGH-CRITICAL
        │
        ▼
release.yml > release-notes (single job, depends on publish)
        │
        └── softprops/action-gh-release ─► GitHub Release at /releases/v1.2.3
                                            (autogenerated changelog + image pull commands)
```

**Beta channel:**

```
git push origin release/beta-1.2.0
        │
        ▼
release.yml > publish (matrix: api, mcp, web)
        │
        ├── Compute beta version ─► steps.beta.outputs.version=1.2.0
        ├── metadata-action ─► tag list {1.2.0-beta, 1.2.0-beta.<run>, beta}
        ├── build-push ─► ghcr.io/<owner>/<repo>/<service>:<each tag>
        ├── sbom-action ─► sbom.spdx.json
        ├── cosign sign / attest ─► signature + SBOM attestation
        └── trivy ─► pass / fail-on-HIGH-CRITICAL

release-notes does not run (skipped by `if: startsWith(github.ref, 'refs/tags/v')`).
```

## Error Handling

| Failure mode                              | Behaviour                                                      |
| ----------------------------------------- | -------------------------------------------------------------- |
| Build failure for one service             | Other services in the matrix continue (`fail-fast: false`)     |
| Push 401/403                              | Job fails; permissions misconfigured — see permissions block   |
| Cosign OIDC failure                       | Job fails; `id-token: write` missing or repo OIDC misconfig    |
| Trivy finds new HIGH/CRITICAL             | Job fails after push; image is in registry but unverified. Operator decides: add to `.trivyignore` with justification, or wait for upstream fix and re-tag |
| Tag re-push (`v1.2.3` exists already)     | `build-push-action` overwrites — accept this; semver tags are not supposed to be re-pushed but blocking it adds friction without preventing the underlying mistake |
| Beta branch named without version suffix (`release/beta-`) | `Compute beta version` step sets `version=""`; metadata-action's `enable` flags evaluate false; **no tags are emitted, build-push fails**. Operator must rename the branch. This failure mode is intentional — a malformed branch should not silently produce an unversioned beta image |
| `release-notes` job fails after `publish` succeeds | Images and signatures are already in the registry; Release page is missing. Operator can re-run `release-notes` job manually from the GitHub Actions UI, or create the Release by hand. The actual deployment artefact is unaffected |

The "Trivy fails after push" ordering is deliberate: scanning the actual
pushed manifest catches arch-specific issues that a pre-push local scan
would miss, and the release is recoverable (delete tag, re-cut, or whitelist).

## Testing Strategy

CI/CD pipelines are notoriously hard to unit test. Layered approach:

1. **Static lint** — `actionlint` invoked locally before commit catches the
   80% of YAML mistakes.
2. **Smoke build (existing)** — `ci.yml`'s docker-build job already proves
   the Dockerfiles compile each image on `linux/amd64`. That gate runs on
   every PR and continues unchanged. It does **not** test multi-arch or push
   paths — those are validated by the first real release.
3. **Beta channel as dry run for stable** — beta is also the natural
   integration test for the workflow itself. Pushing to a
   `release/beta-0.0.0` branch exercises the full publish path (multi-arch
   build, push, sign, attest, scan) without committing to a public stable
   version. Use this before the first stable tag.
4. **Post-release verification** — the runbook lists the exact
   `cosign verify` and `docker pull` commands a maintainer can run to
   confirm a release is well-formed. The auto-generated GitHub Release page
   includes these commands inline.

## Out of Scope

- Native `ubuntu-24.04-arm` runners (QEMU is fine until build time becomes
  a real pain point; switching is purely additive)
- Edge / `main` channel images and PR-preview images
- Auto-deploy after publish to a live environment
- `release-please` / conventional-commits-driven version automation — the
  built-in `generate_release_notes` covers the immediate need; adopting
  `release-please` later is purely additive
- Branch protection rule changes (separate concern; not part of CI/CD wiring)

## Risks

| Risk                                                       | Likelihood | Mitigation                                                          |
| ---------------------------------------------------------- | ---------- | ------------------------------------------------------------------- |
| First release wallclock is long (~25–35 min cold cache)    | Certain    | Documented in runbook; subsequent releases are much faster          |
| Trivy noise blocks an otherwise-good release               | Medium     | `.trivyignore` is the documented escape valve                       |
| GHCR packages stay private after first push                | Certain    | Runbook step calls out the manual visibility flip                   |
| QEMU arm64 build hits a Rust toolchain bug                 | Low        | Fallback plan: temporarily drop arm64 from the matrix and re-tag    |
| Cosign keyless requires repo to be public-OIDC-eligible    | Low        | GitHub-hosted runners on a public repo on github.com — supported    |
| Long-lived beta branches accumulate many runs (storage)    | Low        | GHCR retains all immutable `*-beta.<run>` tags. Mitigation: GitHub package retention policy (separate, not configured here) — out of scope until it actually matters |
| Autogenerated release notes miss commits not landed via PR | Low        | GitHub's algorithm uses commits between tags, not just merged PRs, so direct merges are still picked up. Conventional-commits style helps grouping |
